# Regatta UX Audit — Phase-S Self-Host Loop

> **Purpose**: Derive a UX criteria rubric for what makes regatta delightful to operate, then score the current product against it. Phase-S scope only (single operator, single repo, CLI + dashboard).
>
> **Method**: 4 parallel inventory agents (CLI/config, dashboard, orchestrator, PR/CI/integrations) → criteria synthesis → scoring → ranked gap list. Adversarial review appended at §6.
>
> **Out of scope**: Phase-X (multi-tenant, RBAC, billing, htmx UI rebuild, Sigstore).

---

## 1. UX Criteria Rubric (north-star)

Ranked by load on operator attention. Each criterion is falsifiable — score is **0 / 1 / 2** per surface (0 = absent/broken, 1 = present but friction, 2 = delightful).

### A. First-touch + setup
1. **First-run wizard or single-command boot** — from `git clone` to running daemon in ≤3 commands without reading docs.
2. **One auth, not six** — single sign-in covering GitHub + Anthropic; OAuth/device-flow > paste-token. Operator never juggles 6 HMAC env vars to start.
3. **Doctor catches what serve will hit** — `regatta doctor` MUST fail on every condition that `regatta serve` would also fail on, with the exact same diagnostic + remedy. No "boot fails after doctor passes".
4. **Sensible defaults: 0 required env vars** — fresh clone + `regatta serve` boots in stub mode without setting anything. Required vars surface progressively as features are enabled.

### B. Responsiveness + freshness
5. **Live, not polled** — UI reflects state changes within 1s of the underlying event. Polling intervals ≤2s OR push-based (SSE/webhook).
6. **CI signal proportional to CI cost** — when a PR is open, regatta knows its CI status without the operator refreshing. Failed CI surfaces before operator returns to check.
7. **No silent stalls** — every wait has a visible deadline, a heartbeat, and a path to recovery. "agent up 25 min, last tick 25 min ago" is unacceptable telemetry.
8. **Loading + stale states visible** — operator never confuses "this is the current state" with "this is the last fetched state". Loading indicator on every polled surface.

### C. Intervention
9. **Read-write dashboard** — kill, retry, pause, force-merge, bump priority — all from the surface where the operator first sees the problem. CLI is a backup, not the only path.
10. **One-click context** — clicking an agent / PR / event lands on the GitHub PR, the local log, OR the substrate event payload, no copy-pasting IDs.
11. **Recovery is one step** — agent stuck → click "kill + retry" → done. Not "ssh to box, kill pid, sqlite update, restart serve".

### D. Signal hierarchy
12. **Failures are unmissable** — CI red, agent crashed, budget exhausted, auth broken — all surface louder than green-path noise. Color + position + animation, not 12pt italic gray.
13. **Spend is real-time and per-agent** — operator sees "this run cost $X" before the run finishes, not 24h post-hoc reconciliation drift.
14. **Cost-bounded by default** — `safety.spend_cap_usd` enforced live; PR halts on cap with visible reason. No "discovered $400 burned after the fact".
15. **One panel, one job** — operator scans dashboard left-to-right and knows: what's running, what's broken, what's costing money, what's next.

### E. Naming + discoverability
16. **Names match operator mental model** — "agent" not "subagent worker pid", "stuck" not "non-terminal heartbeat staleness", "spend" not "token_spend reconciliation drift". Test: read a panel label without reading code.
17. **Flags grouped + categorized** — `regatta serve --help` shows flags by group (db, timing, spawner, network), not 18 flat bullets.
18. **One way to do each thing** — three env vars for the same key, two HMAC keyrings, two issue sources, two cost paths — operator picks wrong, debugs.

### F. Mobile + accessibility
19. **Phone-readable** — operator can triage from a phone (commute, off-hours). Single-column responsive, key signal above the fold.
20. **Keyboard-driven** — Escape closes drawers, ↑↓ navigates lists, `/` focuses search. Mouse-only is a fail.

### G. Trust + safety
21. **Destructive actions confirm** — kill agent, force merge, drop DB — all require explicit confirm with stake summary.
22. **Audit trail per action** — every operator action produces a substrate event with actor + before/after state.

## 3. Ranked findings (top 12 wedges, severity × leverage)

> Severity = how much it hurts the operator daily. Leverage = how many criteria improve when this lands. Rough ROI = how much delight per engineer-day.

### F1. 🔴 Dashboard is read-only (criterion #9, #11)
**Pain**: Every recovery requires shelling out to CLI or sqlite. "Agent stuck → click kill" is the difference between a tool and a database viewer.
**Effort**: M-L (5-8 PRs: add POST routes, CSRF, action audit events, undo buffer).
**Fix sketch**: Per-row action buttons (kill / retry / withdraw / force-merge / pause-lane). Add `POST /ui/actions/agent/:id/withdraw` with HMAC token + confirm dialog + substrate event.

### F2. 🔴 No live notifications on CI failure (criterion #6, #12)
**Pain**: Operator enables automerge → CI flakes post-automerge → PR stuck in OPEN/BLOCKED for hours. Hit ≥2× this session per memory.
**Effort**: S-M (webhook receiver or push to OS notification / Slack).
**Fix sketch**: Already partially scoped in #1229 (webhook-wake). Pair with desktop notification on `pr.ci_failed` substrate event. Slack-out as Phase-S+ feature behind config flag.

### F3. 🔴 No "sign in with Claude" + 6-mechanism auth jungle (criterion #2, #4, #18)
**Pain**: First-run requires 3-6 env vars; HMAC has 3 env var variants for the same key; approval keyring is a parallel surface with confusingly similar names. Onboarding-killer.
**Effort**: L (refactor: collapse `REGATTA_HMAC_KEY` / `_KEY_ENV` / `_KEYRING` into one resolver; add Claude OAuth device flow; collapse approval keyring into brief keyring with namespaced key IDs).
**Fix sketch**:
- One env var: `REGATTA_HMAC_KEY` (hex or path-to-file or `keychain:` prefix).
- One auth: `regatta login` → OAuth device flow for Anthropic; `gh auth status` reuse for GitHub. No raw token paste path.
- Doctor reports the actual triplet: GitHub ok | Anthropic ok | HMAC ok.

### F4. 🟠 Silent stalls + heartbeat decoupling (criterion #7)
**Pain**: 2 fixes shipped in last 24h for the same class of bug (#1218, #1227). Heartbeat alive while worker goroutine wedged on synchronous IO = false-OK. Root cause is architectural (per-goroutine heartbeats, not whole-process), not per-bug.
**Effort**: M (worker-loop wrapper that emits per-loop heartbeat with last-progress timestamp).
**Fix sketch**: `obs.WorkerLoop(name, fn)` wraps every long-running goroutine; emits `loop.tick` event every N seconds; orchestrator declares loop stuck if tick > 3×expected interval. Dashboard surfaces "wedged loops" prominently. Promote in-memory pattern from §recent context as canonical rule.

### F5. 🟠 Per-agent live spend invisible (criterion #13, #14)
**Pain**: Operator sees "Today: $12" 30s-lagging aggregate. Cannot tell which agent is burning, cannot halt the burner. Discovery happens in next-day reconciliation.
**Effort**: M (per-agent token_spend running sum, dashboard column, halt-on-cap event).
**Fix sketch**: Add `Agent.spend_micros` running counter updated on every model call. Agents-panel adds "$X.XX" column. Pipeline shows top-3 burners. Live halt on `agent.spend > work_item.budget`.

### F6. 🟠 Failures look like idle (criterion #8, #12, #15)
**Pain**: Empty state, healthy idle, DB down, adapter misconfigured — all render the same italic gray "no work items found". Operator cannot triage at-a-glance.
**Effort**: S-M (per-panel error annotations; failure-aware empty states; top-of-page health summary).
**Fix sketch**: Each panel renders 4 distinct states: loading / healthy-idle / failure / data. Above-the-fold "incidents" bar — red badge if anything broken — operator sees in 200ms whether to act or close the tab.

### F7. 🟠 Polling intervals + GraphQL quota burn (criterion #5)
**Pain**: 30s/2s polls eat 5000/hr GraphQL quota; depletes in single session per session memory 2026-06-10.
**Effort**: S-M for short-term (#1231 ETag) + M-L long-term (#1229 webhook-wake, #1230 SSE).
**Fix sketch**: Already filed as #1229 / #1230 / #1231 / #1232. **Recommend**: ship #1232 (ETag + `gh checks --watch` + GraphQL bundle) first — 80% of value, 5% of effort. Defer SSE rebuild until single-operator pain proves it.

### F8. 🟠 Operator mental model leaks schema/research terms (criterion #16)
**Pain**: "L0 gate", "substrate", "ProgramBrief", "rejection_count" — useful for code review, hostile for operator UX. Operator reads "L4 gate verdict" and shrugs.
**Effort**: S (rename pass on operator-visible strings + flags + dashboard labels; keep internal types unchanged).
**Fix sketch**: User-visible vocabulary lock-down. "Check", "Run", "Plan", "Retry count" replace internal terms. Internal Go types keep their names. Single PR sweeping `internal/web/templates/` + `regatta --help` text.

### F9. 🟡 Recovery is multi-step (criterion #11)
**Pain**: Stuck agent → `regatta agents list` → grep ID → `sqlite3 regatta.db "UPDATE ..."` → `regatta serve` reload. 4 steps + raw SQL.
**Effort**: S (CLI command `regatta agents withdraw <id>` + dashboard button).
**Fix sketch**: Subsumed by F1. As CLI-first interim: ship `regatta agents kill <id>` / `regatta agents retry <id>` / `regatta merge force <pr>`.

### F10. 🟡 Serve has 18 flags as flat list (criterion #17)
**Pain**: First-time operator scans `regatta serve --help`, sees wall of 18 flags, no idea which 3 matter. Defaults are sane but discoverability is poor.
**Effort**: XS (group flags in help output by category).
**Fix sketch**: Modify `parseServeFlags()` help text to emit grouped sections: `# Database`, `# Timing`, `# Spawner`, `# Network`, `# Observability`, `# Experimental`. 1-PR change.

### F11. 🟡 Drawer keyboard nav missing (criterion #20)
**Pain**: Power operator opens drawer w/ click, can't close w/ Escape, must mouse-back. Small but constant friction.
**Effort**: XS (add Escape handler + focus trap).
**Fix sketch**: `layout.tmpl` script block: `document.addEventListener('keydown', e => { if (e.key === 'Escape') document.getElementById('drawer-mount').innerHTML = ''; });`. Add `tabindex` + `autofocus` on drawer close button.

### F12. 🟡 No phone-readable triage view (criterion #19)
**Pain**: Operator off-laptop cannot triage. Mobile drawer = 100% width + grid cramped underneath.
**Effort**: S-M (single-column mobile layout w/ "incidents" feed at top).
**Fix sketch**: Below 768px: collapse all panels to a single "incidents + agents" feed sorted by severity. Hide pipeline/flow grids (not actionable on phone). Promote `running:N | broken:M | spend:$X` ticker to top.

## 6. Adversarial review

You wrote a rubric audit. You did not write a UX audit. The difference is the reason a paying operator switches to a competitor in week three. A senior product designer reviewing regatta cold against Linear / Vercel / Fly / Stripe would not start with a 22-row matrix; they would time how long it takes a stranger to get one PR merged, and they would have an answer in seconds, not paragraphs. You have no such number anywhere in this document. That is the headline failure of the audit itself.

**The single biggest UX failure regatta has, and you missed it**: there is no concept of "what is this thing right now?" A new operator who runs `regatta serve` for the first time has no idea whether anything is supposed to be happening. There is no zero-state tutorial run, no "click here to file your first wedge", no sample issue auto-seeded in a stub mode. Vercel deploys a hello-world the first time you log in. Fly gives you a `fly launch` that produces a running URL in 90 seconds. Stripe gives you test-mode data pre-populated. Regatta gives you `regatta init` (a YAML scaffolder, per `cmd/regatta/init.go`) and then a daemon that needs three env vars and a real GitHub repo with real issues labeled in a real way to do literally anything observable. Your criterion #1 ("First-run wizard") scored 🟡 because `regatta init` exists. That is a ❌. `regatta init` is not onboarding; it is a config-file generator. There is no end-to-end "git clone → first agent dispatched → PR opened" path under 10 minutes, and you did not measure or claim one. Downgrade #1 to ❌ and add a new criterion: "**Time to first merged PR for a new operator**" — target ≤30 minutes, current state likely ≥4 hours including GitHub app setup, Anthropic billing, repo labeling, and label-router config.

**Criteria you are missing entirely, ranked by what a competitive tool would have**:

1. **Search** — there is no `/` search across agents / events / work-items / PRs. Grep'd the routes in `internal/web/dashboard.go` — zero search endpoints. Datadog, Sentry, Linear: search is the primary navigation. You scored #20 (keyboard) ❌ for missing `/` focus, but the deeper failure is there is nothing to focus to.
2. **Command palette** — no cmd-K. Linear, Vercel, Stripe, GitHub all have this. For a tool that has 30+ CLI subcommands (counted `cmd/regatta/*.go`: `agents`, `approval-decide`, `approval-list`, `audit`, `cost`, `digest`, `doctor`, `doctor-live`, `events`, `init`, `install-service`, `keys`, `l0`, `merge-status`, `program`, `program-inspect`, `reload-secrets`, `resume`, `review-status`, `secret`, `selfimprove`, `serve`, `status`, `triggers`, `uninstall-service`, `validate-config`, `verify-repo-config`) and zero in-product discovery surface, this is a blocking gap.
3. **Dark mode** — grep'd `internal/web/templates/layout.tmpl`: zero hits on `dark`, `theme`, `prefers-color-scheme`, `localStorage`. Operators run dashboards 8+ hours a day; missing dark mode in 2026 is table-stakes, not aspirational. You did not score this.
4. **UI state persistence** — which panel was open, which filter applied, which drawer last viewed? Zero `localStorage` in templates means every reload wipes operator context. Linear restores tab state per workspace.
5. **Sharable URLs for views** — can you send a teammate a link to "agent #47 right now"? Drawer state is not in the URL (the routes are `/ui/drawer/agent/` with path-param, but the dashboard root does not deep-link). No filter-as-query-param. No "incident snapshot" permalink.
6. **"What changed since I last looked?"** — Sentry, Linear, GitHub all have unread/changed badges. Regatta has none. Operator returns after lunch, scrolls the events panel, hopes to spot what's new.
7. **Undo** — no undo on any action. Once read-write actions land per F1, this matters immediately. Stripe and Linear both have toast-with-undo.
8. **In-product changelog / "what's new"** — none. Operators upgrading regatta have no idea what changed.
9. **Empty-state design** — you mention "failures look like idle" (F6) but the deeper problem is empty states are not designed at all. There is no "no events yet — here is how to file your first wedge" content. Stripe's empty states teach the product.
10. **Error message quality** — when `regatta serve` fails, does the message tell the operator what to do next? You did not audit this. Spot-check `wire_web.go:54` per your own citation — does it say "set `REGATTA_HMAC_KEY` like this: `export REGATTA_HMAC_KEY=$(openssl rand -hex 32)`"? Or does it say "ui handler init: hmac key not configured"? The latter is a slog dump, not an error message. This deserves its own criterion: "**Errors carry remediation, not just diagnosis**".

**Where you are bullshitting yourself on scoring**:

- **#1 First-run wizard 🟡 → ❌**. As above. `regatta init` is a scaffolder. No end-to-end first-success flow exists.
- **#3 Doctor 🟡 → ❌**. You admit in the note that doctor doesn't report mode-specific env vars and the `--ui=true` boot error doesn't suggest the fallback. That is the entire job of doctor. It fails its purpose. ❌.
- **#5 Live, not polled — Dashboard 🟡 → ❌**. 2-30s polling is not "live with friction"; it is polling. The criterion text says "≤2s OR push-based". 30s spend panel violates the criterion. ❌.

- **#15 One panel, one job 🟡 → ❌**. You note "pipeline + agents + flow + work-items all show subsets of the same state from different angles" and "broken state and idle state look identical." That is the definition of failing this criterion. ❌.
- **#22 Audit trail ✅ → 🟡**. Substrate events exist and `audit verify` exists, but the operator-visible audit is buried behind a CLI. There is no "who did what when" view in the dashboard. The data exists; the UX does not. ✅ requires both.

The term leaks into substrate event kinds (`l0.evaluated`, `l0.passed`), into config keys, into spec adapter contracts, into the `cmd/regatta/l0.go` subcommand name itself, into PR-body footers the reviewer-verdict gate parses, into half a dozen tracking issues. - **F1 dashboard read-write, scored M-L**. You wrote "5-8 PRs: add POST routes, CSRF, action audit events, undo buffer." You forgot: rollback semantics (what does "kill agent" do to the in-flight model call?), idempotency (operator double-clicks kill, what happens?), permission model (currently HMAC-only, no user concept), confirm-dialog UX, and the fact that every action button needs a loading + success + failure state per F6 which you also scored S-M. This is your F6 + F12 + F1 + F2 collapsed into the smallest viable shippable artifact, and it is the single highest-leverage UX win. Ship this before any of your QW1-QW8.

**Doc structure failure**: an engineer reading this would not know what to build first because you ranked by "severity × leverage" without timelines, without dependencies, and without a single number that says "current time to first merged PR is X, target is Y." Without that anchor the whole rubric floats. Add a §0 "**Current state in one number**" — e.g. "30-min onboarding, 12 daily friction events per operator hour, 0 mobile sessions possible" — and rerank everything against moving those three numbers.

> **Method**: Dry-run walk of a fresh operator path from `git clone` to "regatta merges its first PR." ### 7.3 Where the operator gives up

**Step 11 (branch protection)** is the most likely abandon-point. Solo operators cannot satisfy `required_approving_review_count>=2` without a second account or disabling the check. Regatta's safety model requires L6 = human merge under branch protection; this is the architecture, not an oversight. But the quickstart does not warn that the canonical recipe is structurally incompatible with single-operator self-host. The operator hits `regatta verify-repo-config` FAIL, reads `docs/operator/day1.md` (not opened in this audit but cited from quickstart §3), tries to satisfy the 5 settings, hits "this requires 2 reviewers" — and either turns off the check (defeating the safety model) OR creates a sock-puppet account (against GitHub TOS) OR abandons.

**Step 13–14 (adapter divergence)** is the second-likely abandon. The quickstart §4 walkthrough uses `markdown_catalog`. The init template uses `github_issues`. The operator picks one, follows the other's docs, and the daemon either reads an empty `.regatta/items/` (`github_issues` mode) or returns no GitHub issues (`markdown_catalog` mode + `label:planned`). The diagnostic from the daemon is a slog line saying "0 ready items" — no error, no remediation. Operator stares at the dashboard for 10 minutes, then re-reads the spec adapter docs.

**Diagnostic dead-end**: `regatta serve` boots cleanly even when no work items exist. There is no "you have 0 ready items in the configured adapter — check `spec_adapter.selector`" surfaced in the UI or logs. The dashboard shows an empty pipeline, indistinguishable from healthy idle (§6 F6 finding). This is the moment most operators tab to Discord or file a GitHub issue titled "regatta does nothing."

Top-tier comparator is **90 seconds to running, 2–5 minutes to a useful artifact**. ## 9. Dispatch UX (operator-as-issue-author)

> **Scope**: regatta's primary input surface is *the GitHub issue the operator writes*. The issue body shape, label vocab, and acceptance-criteria format determine whether regatta picks it up, parses it, or silently drops it. This is the operator's content creation UX — and the prior audit ignored it.

### 9.1 What regatta expects in an issue

From `internal/orchestrator/specadapter/parse.go`:

- **Title regex** (required): `^[A-Z][A-Z0-9_-]{1,40}:` — e.g., `RESEARCH:` or `COST_FIX:`. Operator naturally writes `feat: add X` → silently rejected.
- **Metadata block** (optional but load-bearing): YAML inside HTML comment — `<!--regatta\nlane: L2\n-->`. Operator unfamiliar with this dialect.
- **Acceptance criteria** (optional but parsed): `## Acceptance criteria` heading + `- [planned] AC1: text`. The `[planned]` token is regatta-specific; GitHub's default `- [ ]` checkbox is silently ignored.
- **Dedup marker** (auto-inserted by regatta): `<!-- regatta-dedup-key: sha256 -->`

### 9.2 Label vocabulary (from `docs/engineer/briefs/label-sop.md`)

- 25 canonical labels across 5 namespaces: `kind:*`, `severity:*` / `priority:*`, `state:*`, `scope:*`, special.
- Umbrella pattern: title `[wedge] X` + label `kind:wedge`.
- Child pattern: `kind:slice` w/ `Umbrella: #N` in body.
- Operator discovery path: external file + `gh label list`. Not in-product.

### 9.3 Top 10 dispatch UX pain points

| # | Severity | Pain | File:line |
|---|----------|------|-----------|
| 1 | HIGH | No `.github/ISSUE_TEMPLATE/regatta-wedge.md` — operator guesses format | (absent) |
| 2 | HIGH | Parse failure silent — regatta logs WARN, no GH comment, no dashboard panel, no reaction emoji | `specadapter/parse.go` |
| 3 | MED | Title-prefix rule `^[A-Z][A-Z0-9_-]{1,40}:` unstated outside parser code | `parse.go` |
| 4 | MED | Acceptance-criteria `[planned]` token vs GitHub's `[ ]` — silent skip on mismatch | `parse.go` |
| 5 | MED | YAML-in-HTML-comment metadata block is regatta-specific dialect; no help text | `parse.go` |

### 9.4 Single biggest dispatch UX failure

**Silent rejection on parse failure**. Operator files an issue, regatta polls it, parser rejects (bad title prefix / missing `## Acceptance criteria` heading / malformed metadata YAML), regatta moves on. The issue sits open on GitHub forever. No reaction emoji, no bot comment, no label `kind:rejected`, no dashboard "rejected work-items" panel. Operator's only signal: dashboard pipeline stays empty + `regatta events tail --kind=spec.rejected` (if they know to look). Top-tier comparator fix: bot reaction-emoji + sticky comment "regatta couldn't parse this — missing acceptance-criteria block; see template at …".

### 10.2 What regatta could steal — per tool

**Fly.io.** `flyctl status` is the single best terse-status pattern in dev infra: three lines — app health, machine count + per-region distribution, last deploy time + status — answer the operator's "is it ok?" question with zero polling and zero scrolling. Regatta's `regatta status` should mirror this exactly: one line for orchestrator health + tick age, one for `running:N stuck:M queued:K` agent census, one for `last merged: #1227 (4m ago) · CI: 2 green 1 red`. The rolling-deploy progress bar (`fly deploy` shows machine 1/4 → 2/4 → 3/4 with health-check state per machine) is the model for showing parallel-agent dispatch progress — regatta currently shows nothing equivalent while a wave is in flight. Also steal: `fly logs` interleaves machine ID into every line so the operator never loses context when 3 machines log concurrently — regatta's events tail should prefix every line with `[agent-N]` the same way.

**Vercel.** The killer pattern is **deployment URL on every commit**. Every push gets a unique preview URL that's shareable, openable on phone, and tied to the commit SHA in the PR. Regatta's analog: every dispatched agent run should produce a shareable URL (`https://regatta.local/run/<work-item>/<agent-N>`) that deep-links to the live drawer state — solves §6 missing-criteria #5 (shareable URLs) and partially solves #19 (phone-readable, since the URL opens to a triage-focused mobile view). Second steal: Vercel's build log is **streaming with phase markers** (Installing → Building → Deploying → Ready) — regatta's agent log should show similar phase markers (Brief loaded → Spec gate → Implementer running → CI dispatched → PR opened) so the operator knows where in the lifecycle the agent is wedged without reading raw output.

**Linear.** `Cmd+K` command palette is the reference implementation — every Linear action is reachable from one keystroke + fuzzy search, no menu hunting. For a regatta CLI with 30 subcommands (per §7.1 inventory) and zero in-product discovery, this is the single highest-leverage missing feature. Second: Linear's **per-user view state** (last filter applied, last issue opened, sidebar collapsed-or-not) persists across reload via `localStorage` — solves §6 missing-criterion #4 directly. Third: Linear's **changed-since-last-visit badges** on every navigable surface — every list item that's new or changed since the operator's last load gets a colored pip; solves §6 missing-criterion #6.

**GitHub Actions.** Two patterns. (1) **Job-step expand/collapse with log-line anchoring**: every step is a collapsed accordion by default; expanding shows logs with line numbers; each line has a permalink anchor. Regatta agent drawers should adopt this exactly — collapse internal phases, expand on demand, every log line is `#L<n>`-linkable. (2) **`gh run watch` terminal pattern**: live-redrawing TUI showing per-job progress bars in a single terminal window, exits with the run's status code. Regatta has no equivalent CLI live-mode — `regatta status --watch` should redraw a Fly-style three-line summary every 2s, exit code matching pipeline health.

**Datadog.** The pattern worth stealing — and worth being adversarial about, since Datadog itself fails several rubric rows — is **alert-with-context-bundle**. When a Datadog monitor fires, the notification carries (a) the metric graph time-range scoped to the firing window, (b) the dashboard URL pre-filtered to the affected host/service, (c) the runbook link from the monitor config, (d) the recent deploy events overlaid on the graph. Regatta's `pr.ci_failed` event should carry the same bundle: link to the failed PR, the CI step that failed, the agent that produced the PR, and the last 3 events from that agent — operator opens one link, sees everything needed to triage.

### 10.3 Top-5 patterns regatta should adopt (ranked)

1. **`flyctl status`-style 3-line health summary** (Fly). Cheapest, highest-leverage. One above-the-fold line per concern: orchestrator + tick age, agent census, last merge + CI. Mirrors §6's "build this one thing first" recommendation. Effort: S. Criteria moved: #5, #7, #12, #15.
2. **`Cmd+K` command palette** (Linear). Surfaces all 30 CLI subcommands + dashboard actions through one keystroke. Closes §6 missing-criteria #1 (search) and #2 (palette) simultaneously. Effort: M. Criteria moved: #9, #11, #17, #20.
3. **Deployment-URL-per-commit analog: shareable run URL** (Vercel). Every agent run gets `regatta.local/run/<wi>/<agent>` that deep-links live drawer state and is phone-openable. Enables the "send a teammate the link" workflow and the mobile triage path. Effort: M. Criteria moved: #10, #19; closes §6 missing-criterion #5.
4. **Streaming phase-marked log** (Vercel build log + GH Actions job-step). Replace raw event firehose in the agent drawer with collapsed-by-default phase accordions (Brief → Spec → Impl → CI → PR) plus expand-on-demand log with anchor-linkable lines. Effort: M-L. Criteria moved: #7, #8, #10, #16.
5. **Alert-with-context-bundle** (Datadog). Every `pr.ci_failed` / `agent.stuck` / `spend.cap_hit` event ships with a bundle of links (failed step, owning agent, last 3 related events, suggested action). Pairs with #1229-class webhook-wake work already filed. Effort: S-M. Criteria moved: #6, #10, #12; closes §6 missing-criterion #10 (error message quality).

Honourable mention (#6): Linear's **per-user view-state persistence** via `localStorage` + URL deep-links. Closes §6 missing-criteria #4 and #5; should ship alongside #3 above since they share the URL-as-state-handle plumbing.

> **Calibration caveat**: Low-confidence (`?`-flagged) cells — Vercel #3, Datadog #17 — should be confirmed by an operator who runs those products daily before any of the above is treated as a build spec.

### 8.3 `regatta events tail`

**File**: `cmd/regatta/events.go:1–150`

**Surface**: Streaming event log; live-follow mode or bounded query; filters by agent, event kind, time window; outputs table or JSON.

### Recommendation for §8 follow-up

The 12 surfaces above are lower-friction wins than the top-12 wedges in §3 because they are **isolated CLI endpoints** — no dashboard, no auth refactor, no webhook infrastructure. Prioritize in this order:

1. **Surface all state changes in TUI** (status, agents, events, cost): add timestamps + success/failure indicators. Fix via `--once` output format + live refresh loop heartbeat (§3 F4 "heartbeat decoupling" already scoped).
2. **Add operator discovery cues**: help text examples (`regatta agents list --state running`), rule docs (`regatta self-improve rules --docs`), approval examples (`regatta approval decide --help` shows token format).
3. **Collapse manual workflows into commands**: `regatta digest --show` (open in $EDITOR), `regatta install-service --post-check` (run healthz poll inline), `regatta approve --list-stale` (sort by age).
4. **Fix silent successes**: every write command (`set`, `resume`, `digest`, `install-service`) should emit a summary line confirming what changed.

None of these require new infrastructure; all are single-command-file changes or help-text additions. Estimated total effort: **4–6 PRs, ship within 2 weeks alongside the quick-win loop (§4)**.
