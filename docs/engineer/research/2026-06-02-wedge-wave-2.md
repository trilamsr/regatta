# Wedge research — wave 2

Status: research brief (no design, no code)
Date: 2026-06-02
Audience: design-phase agent for the next dossier batch
Scope: seven wedges not present in `docs/wedges/README.md` Phase X index

## Why this brief exists

The Phase X wedge index (cost governor, approval gates, plan-as-code,
conditional DAG, blackboard, unified substrate) covers cross-session
fleet primitives. This brief surveys seven adjacent primitives that
become relevant when regatta widens beyond the dispatch DAG: plan
authoring surface, third-party capability supply chain, observability
neighbours, MCP boundary direction, evaluation rigour, sandbox
runtime, and prompt versioning. Each section ends with an explicit
adopt / build / pass call so the design-phase agent does not
re-search the same ground.

Memory cites: `feedback_research_design_principles` (proven OSS over
build-from-scratch; UX > best-in-class > best-practices > long-term),
`feedback_pr_body_file_only`, `feedback_pr_body_release_notes_mandatory`,
`feedback_deletion_default`.

Scoring axes per candidate (1 low — 5 high):

- Maintenance trajectory — commit cadence + funding signal
- Ecosystem — adapters / integrations / community
- Adoption — public reference users
- Regatta-fit — alignment with cross-session durability story
- Swap cost (inverse — 1 hard to leave, 5 easy) — operator escape hatch

## 1. Workflow language for plans

Today: `.regatta/items/*.md` + frontmatter. The Phase X plan-as-code
dossier picks YAML + CUE validation. This section asks the broader
question: should the *authoring* surface stay markdown, move to
typed code, or stack a DSL on top.

### Prior art adopted

| Candidate | Class | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|
| CUE | DSL (constraints + types) | 4 | 4 | 4 | 5 | 3 |
| Dhall | DSL (functional, total) | 3 | 2 | 2 | 3 | 3 |
| Pkl (Apple) | DSL (OO, typed) | 4 | 3 | 3 | 4 | 3 |
| Nickel (Tweag) | DSL (gradual types) | 3 | 2 | 2 | 3 | 3 |
| KCL | DSL (constraints + collection ops) | 3 | 2 | 2 | 3 | 3 |
| GitHub Actions YAML | YAML + schema | 5 | 5 | 5 | 3 | 4 |
| GitLab CI YAML | YAML + schema | 5 | 5 | 4 | 3 | 4 |
| ArgoCD / Argo Workflows | YAML | 5 | 5 | 4 | 4 | 4 |
| Temporal | Code-as-plan (Go/Java/TS) | 5 | 5 | 5 | 4 | 2 |
| Dagster | Code-as-plan (Python assets) | 5 | 4 | 4 | 3 | 2 |
| Prefect | Code-as-plan (Python decorators) | 5 | 4 | 4 | 3 | 2 |
| Markdown + frontmatter | Doc-as-plan | 5 | 5 | 5 | 4 | 5 |

Notes on ergonomics axes (operator, IDE, VC, type-safety, AI-friendly):

- **Markdown + frontmatter** wins on AI-friendly + diff-readable; loses
  on type-safety. Current default. Cost of leaving: zero.
- **CUE** wins on type-safety + tool-checkable validation; loses on
  IDE depth (LSP exists but thin). Phase X already picks CUE for
  *validation* only — keep that scope.
- **Pkl** has the strongest IDE story (JetBrains + VSCode plugins,
  reflection API, Apple is the maintainer). Cost: smaller community,
  JVM runtime for some tooling.
- **Temporal-class code-as-plan** trades AI-friendliness for runtime
  guarantees. The 2026-06-01 `w9-temporal-vs-bespoke-redteam` doc
  in this repo already concluded against full Temporal adoption.
  Keep that decision; the authoring-surface question is independent.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| Keep markdown + frontmatter as *operator surface*; CUE as *validation layer* (per Phase X plan-as-code dossier). | A `regatta plan lint` command that runs the CUE schema against any plan source format (md, yaml, json). One linter, three readers. | Pkl adoption: revisit if a paying customer files a request for IDE-grade authoring; today, markdown is winning on AI-readability and operator pain is low. |

## 2. Agent skill marketplace

Today: regatta dispatches subagents with bespoke prompts. The
question: should reusable capabilities live in a marketplace format
the operator can install + audit + diff.

### Prior art adopted

| Candidate | Class | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|
| Anthropic Agent Skills (SKILL.md + YAML frontmatter) | Open standard, MCP-adjacent | 5 | 5 | 5 | 5 | 4 |
| MCP server registry (registry.modelcontextprotocol.io) | Registry, canonical metadata | 5 | 5 | 5 | 5 | 4 |
| OpenAI plugins / Custom GPTs | Closed marketplace | 3 | 3 | 3 | 2 | 2 |
| Claude Code marketplace (claudemarketplaces.com) | Community directory | 3 | 4 | 4 | 4 | 5 |
| skills.sh | Community catalogue | 3 | 2 | 2 | 3 | 5 |
| LangChain Hub | Closed-ish, prompt-focused | 3 | 3 | 3 | 2 | 3 |

Key facts (June 2026):

- Anthropic Skills launched 2026-05-01 with ~600 public skills.
  Microsoft (VS Code + GitHub), Cursor, Goose, Amp, OpenCode have
  adopted. SKILL.md = markdown + YAML frontmatter; supporting
  templates/scripts colocated.
- MCP Registry launched 2025-09; ~2,000 server entries by mid-2026.
  Intentionally minimal — no UI, no categories, no search. Acts as
  the DNS layer; user-facing browsing is community work.
- OpenAI plugins are effectively deprecated; Custom GPTs are siloed
  to ChatGPT.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| Anthropic Skill format (SKILL.md) as the *internal* shape for regatta-published agent capabilities. Free, adopted by the toolchain regatta already ships against, and the markdown format aligns with our `.regatta/items/*.md` convention. | A `regatta skill install <ref>` command that resolves either the MCP registry or a Skill URL into a sandboxed install dir per tenant. Permissions live in the existing policy engine. | Building a regatta-branded marketplace: reopen only if cross-operator demand surfaces (≥3 operators ask for cross-tenant skill sharing). Today, lean on Anthropic's directory + MCP registry. |

## 3. Observability vendor ecosystem alignment

Today: regatta has its own OTel backbone (`2026-05-31-mvp-3-w6-otel-backbone`).
The question: which third-party vendor do we *interop with* by default
so an operator with an existing observability stack can plug regatta
spans into it.

### Prior art adopted

| Candidate | Class | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|
| Honeycomb | OTel-native, generalist | 5 | 5 | 4 | 5 | 4 |
| Datadog APM (LLM Observability) | Commercial APM, OTel GenAI native | 5 | 5 | 5 | 4 | 3 |
| Grafana / Tempo / Loki | OSS OTel stack | 5 | 5 | 4 | 5 | 5 |
| Langfuse | LLM-specific, MIT, self-hostable | 5 | 4 | 4 | 4 | 5 |
| Helicone | LLM-specific, Rust gateway, OSS | 4 | 3 | 3 | 3 | 4 |
| Arize Phoenix | LLM eval + obs, OSS (OpenInference) | 4 | 4 | 3 | 4 | 4 |
| Braintrust | LLM eval + prompt + obs, commercial | 4 | 4 | 4 | 4 | 3 |
| New Relic | Commercial APM, OTel GenAI | 4 | 4 | 4 | 3 | 3 |

Key fact: OTel GenAI semantic conventions exited experimental for
client spans in early 2026. Datadog, Honeycomb, Grafana, Jaeger v2,
LangSmith, OpenLLMetry, Langfuse, New Relic all map to the same
`gen_ai.*` namespace. The vendor lock concern is structurally lower
than it was 12 months ago — choosing a primary vendor no longer
forces an operator into a one-way door, provided regatta emits OTel
GenAI spans natively.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| **Primary: Honeycomb** (OTel-native, generalist, no LLM-specific lock-in, regatta's existing backbone exports there cleanly). **Fallback: Grafana/Tempo OSS stack** for self-host operators. **LLM-specific co-pilot: Langfuse** (MIT, self-hostable, drops in next to either). | A documented "swap vendor" runbook that points the OTel collector at a different backend. No vendor-specific code in regatta core. | Picking Datadog/Braintrust as default: reopen only if a paying customer mandates it. Both are commercial closed-source; choosing them as the primary path costs operator escape velocity. |

## 4. MCP server ecosystem — direction of integration

Today: regatta consumes some MCP servers (GitHub, Slack) ad-hoc.
The question: should regatta also *expose itself* as an MCP server
so operator IDEs can dispatch directly.

### Prior art adopted

| Candidate | Pattern | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|
| GitHub MCP server (official) | regatta-as-client | 5 | 5 | 5 | 5 | 5 |
| Slack MCP server (Slack-owned + community) | regatta-as-client | 5 | 4 | 4 | 4 | 5 |
| modelcontextprotocol/servers (reference impls) | regatta-as-client | 5 | 5 | 4 | 4 | 5 |
| mcp-gateway-registry (agentic-community) | regatta-as-server, behind gateway | 3 | 2 | 2 | 3 | 4 |
| Microsoft 365 Declarative Agents | bi-directional widget | 4 | 3 | 3 | 2 | 2 |
| Composio MCP toolkits | regatta-as-client via SaaS | 4 | 4 | 3 | 3 | 4 |

Trade-offs of bi-directional MCP:

- **Pro:** inverts the absorption risk — Claude Code becomes a regatta
  *client* (operator's IDE invokes regatta dispatch / approval / budget
  via MCP), so the cross-session moat compounds rather than competes.
  Already noted in `docs/wedges/README.md` "Recently surfaced" list.
- **Pro:** JSON-RPC bi-directional channel allows server-initiated
  notifications (approval requests pinging back into the IDE).
- **Con:** latency overhead vs direct API calls (the reasoning layer
  adds round-trips).
- **Con:** authorization surface widens — every MCP-exposed verb is
  a tool an autonomous agent can invoke. Approval gates have to be
  enforced inside the MCP handler, not at the UI.
- **Con:** schemas are LLM-tuned, awkward for bulk or paginated reads.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| **Consume** GitHub + Slack reference MCP servers for the existing notify/PR-touch paths (already partly done). **Expose** a *minimal* read-only MCP surface on regatta: `list_runs`, `get_run`, `get_budget` first. | Authn/authz inside the MCP handler — every exposed verb runs through the policy engine. Write verbs (`dispatch`, `approve`) gated behind explicit operator opt-in flag per tenant. | Full bi-directional write surface: reopen when the read-only surface has been used by ≥2 operator IDEs for ≥30 days without a security incident. Premature write exposure is the load-bearing risk. |

## 5. Agent-eval frameworks

Today: regatta has no continuous eval suite for the agent quality of
its dispatched workers. The question: which suite do we adopt, and
how does it integrate into the dispatch loop.

### Prior art adopted

| Candidate | Class | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|
| SWE-bench Verified | Real-repo coding tasks | 5 | 5 | 5 | 5 | 5 |
| SWE-bench Live | Contamination-resistant variant | 4 | 3 | 3 | 4 | 5 |
| SWE-bench Pro | Harder task set | 4 | 3 | 3 | 4 | 5 |
| Multi-SWE-Bench | Multi-language extension | 3 | 2 | 2 | 3 | 5 |
| HumanEval / MBPP | Single-function Python | 5 | 5 | 5 | 1 | 5 |
| GAIA | General assistant tasks | 4 | 3 | 3 | 3 | 5 |
| AgentBench | Multi-task agent eval | 3 | 3 | 3 | 3 | 5 |
| LangChain evals (LangSmith) | Trace-tied eval, vendor-bound | 4 | 4 | 4 | 2 | 2 |
| HELM (Stanford) | Holistic LM eval | 3 | 3 | 3 | 2 | 5 |
| MMLU | Knowledge eval, saturated | 3 | 5 | 5 | 1 | 5 |

Key fact: HumanEval (90%+) and MBPP (saturated) no longer
discriminate frontier models on coding tasks. SWE-bench Verified
(Claude 4 Sonnet 77.2%, GPT-5 74.9%, Gemini 2.5 71.8% as of 2026)
remains the discriminating benchmark for code-fixing agents — the
exact shape of regatta-dispatched workers.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| **SWE-bench Verified** as the canonical worker-quality benchmark; emit a Datadog/Honeycomb tag per dispatch carrying the worker model + score percentile so operators see quality drift. | A `regatta eval run` subcommand that pins a worker config (model, prompt version, tool set) and runs SWE-bench Verified in a sandbox (see §6) on cron. Output → blackboard fact + OTel span. | Building bespoke evals: reopen only when an operator surfaces a workflow SWE-bench cannot model (e.g. multi-tenant security review). Leaning on the open benchmark first means zero curation cost. |

## 6. Sandbox runtimes

Today: self-host = local subprocess; SaaS plans (not yet shipped) want
a cloud sandbox. The question: which canonical sandbox does regatta
SaaS dispatch into.

### Prior art adopted

| Candidate | Class | Cold start | Maint. | Eco. | Adopt. | Fit | Swap |
|---|---|---|---|---|---|---|---|
| E2B | Firecracker microVMs, AI-focused | ~90-150ms | 5 | 5 | 5 | 5 | 4 |
| Daytona | Docker containers, dev-env-focused | 27-90ms | 5 | 4 | 4 | 4 | 4 |
| Modal | GPU-capable containers | ~500ms-2s | 5 | 4 | 4 | 4 | 3 |
| Vercel Sandbox | Vercel runtime sandbox | ~200ms | 5 | 4 | 3 | 3 | 4 |
| Blaxel | Firecracker, fastest cold start | ~25ms | 3 | 2 | 2 | 3 | 4 |
| Coder | Dev environments, self-host-friendly | seconds | 5 | 4 | 4 | 3 | 5 |
| GitHub Codespaces | Hosted dev env | seconds | 5 | 5 | 5 | 2 | 4 |
| Local Docker | Self-host default | ~1-5s | 5 | 5 | 5 | 5 | 5 |

Key facts:

- E2B has the deepest agent-runtime ecosystem (Firecracker isolation,
  Python + JS SDK, AI-vendor partnerships). Best fit for "regatta
  dispatched a worker, the worker needs to run code."
- Daytona wins on cold start but is positioned as a persistent dev
  environment, not a one-shot exec sandbox.
- Modal is the only candidate that can hold a GPU in the sandbox —
  matters if a regatta worker fine-tunes or runs inference locally.
  Out of scope for MVP.
- Local Docker covers the self-host case today and need not change.

### Decision row

| What to adopt | What to build | Pass + reopen condition |
|---|---|---|
| **Self-host: local Docker subprocess** (no change). **SaaS canonical: E2B.** **Future GPU lane: Modal** when an operator demand surfaces. | A pluggable `Sandbox` interface with two reference impls — local-docker + E2B — gated by a `regatta.toml` `sandbox.kind` field. Replay-grade artefact capture is the contract; the sandbox is interchangeable. | Switching to Daytona / Blaxel: reopen when cold-start latency becomes the dispatch-loop bottleneck (today it is not — the LLM call dominates). |

### Decision row

| What to adopt | What to build | Pass + reopen condition |

Eval results feed back into §5 OTel tags. | Adopting Braintrust / LangSmith: reopen only when an operator needs cross-team prompt sharing with web UI (today, PR diff covers it). |

## Top-3 recommended wedges

Ranked by impact (cross-session moat depth) × inverse cost (smaller =
better) × reopen-cost (lower if we skip = better).

1. **Expose regatta as MCP server (read-only first)** — §4. Inverts
   the absorption risk against Claude Code Dynamic Workflows. Low
   build cost; high strategic payoff; the read-only first stance
   contains the security surface. Maps to the "MCP server as the
   integration surface" item in `docs/wedges/README.md` "Recently
   surfaced."
2. **SWE-bench Verified as worker-quality gate** — §5. Low build
   cost (we adopt the public benchmark wholesale), high operator
   trust payoff (drift-detection visible in the existing OTel
   backbone). Composes with the cost-governor wedge: budget per
   eval-score band.
3. **Anthropic Skill format for regatta-published capabilities** —
   §2. Low build cost (markdown + frontmatter, same shape we use
   today), high ecosystem leverage (Microsoft + Cursor + Goose
   already speak the format). Skip building a regatta-branded
   marketplace; lean on Anthropic's directory.

The other four wedges (workflow language, observability vendor
alignment, sandbox runtime, prompt versioning) are reads we should
*reuse* (markdown + CUE, Honeycomb + Langfuse, local Docker + E2B,
Promptfoo) rather than build — each section's decision row records
the pass and reopen condition.

## Adversarial review pass

Run on this brief by a separate subagent. Findings folded back in:

- **Vendor-lock concern on §3 (Honeycomb primary):** flagged that a
  commercial primary contradicts the self-host-first stance. Resolved
  by naming Grafana/Tempo as the explicit fallback for self-host
  operators and Langfuse as the LLM-specific co-pilot — both OSS.
- **MCP write-verb risk on §4:** flagged that exposing `dispatch` /
  `approve` over MCP is a privilege escalation path. Resolved by
  scoping the v1 surface to read-only and gating writes behind an
  explicit per-tenant opt-in flag.
- **SWE-bench saturation drift on §5:** flagged that 77% scores are
  approaching the ceiling. Resolved by adding SWE-bench Live and
  SWE-bench Pro as the contamination-resistant + harder fallbacks
  in the table; the eval subcommand should be benchmark-pluggable.
- **Promptfoo + CAS overlap on §7:** flagged that "extend CAS with a
  `prompt_revision` tag" could conflict with the blackboard wedge's
  CAS schema. Resolved by deferring the schema choice to the
  blackboard dossier; Promptfoo adoption is independent.
