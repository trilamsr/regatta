## Findings ranked by load-bearing weight

### F1 — Top-3 mis-sequenced against PR #399 customer-0 (BLOCKING)

PR #399 picks **persona A = solo OSS maintainer of a single large
repo** as customer 0, with a top-3 of (W7 htmx UI, init-bundle, Gitea
SCM adapter). None of those appear in this brief's top-3. The brief's
three picks (MCP-server, SWE-bench, Skill format) instead serve
persona B/C/D — which #399 explicitly sequences as MVR-2/3/4.

Concrete trace:

- **MCP-server expose:** Persona A is a solo OSS maintainer. The
  "IDE dispatches regatta via MCP" pattern requires an IDE-as-control-
  plane operator, which is persona B (internal-tooling team) or C
  (platform vendor). Persona A reviews on phone (#399 §2 G2) and
  dispatches from cron/issues, not from VS Code's MCP panel.
- **SWE-bench gate:** Persona A's eval surface is "did the green PR
  merge?" — already covered by `pr_merge_rate` in #399 §5 Gate 1.
  SWE-bench Verified adds a synthetic eval persona A does not run.
- **Skill format:** Persona A has one repo with one skill set
  (`.regatta/items/*.md`). Skill *publishing* is a persona B/C
  marketing primitive, not a persona-A unblock.

The brief does not cite PR #399 once. Sections 1-7 are valid research;
the **top-3 ranking** assumes a different customer 0.

**Fix:** add a §0 customer-0 alignment note that explicitly
re-sequences the top-3 against #399's MVR-1/2/3/4 phases — or change
the top-3 to wedges that unblock persona A within MVR-1. Per
`feedback_research_design_principles` UX > best-in-class:
engineering-elegance picks lose to customer-0-pain picks.

### F2 — SWE-bench measures the wrong primitive (BLOCKING)

Section 5 picks SWE-bench Verified as "the canonical worker-quality
benchmark." This conflates two distinct primitives:

- **Worker-quality:** the dispatched Claude/GPT/Gemini agent's
  patch-correctness on a closed task. Regatta does NOT differentiate
  here — explicitly anti-wedge in `docs/wedges/README.md`
  ("Smarter prompts or planners — model-vendor territory").
- **Reviewer-quality:** the L4 adversarial-reviewer-gate's
  discrimination — does it catch bad PRs without false-flagging good
  ones? This IS regatta's differentiator (`2026-06-01-self-host-first.md`
  S2-T2 "Adversarial reviewer subagent → first-class gate L4").

SWE-bench Verified evaluates the **first** primitive. Adopting it as
the canonical gate gives regatta a number it does not produce — the
score moves with model-vendor releases, not with regatta code. The
moat is invisible in the metric.

**Fix:** rename the pick to **"adopt SWE-bench Verified as a
*reviewer-discrimination* eval"** — feed both passing and
adversarially-mutated SWE-bench patches through the L4 reviewer, score
precision/recall on caught-bad / passed-good. That eval is
regatta-specific and the score moves with regatta code, not vendor
releases. The brief's §5 reopen condition ("workflow SWE-bench cannot
model — e.g. multi-tenant security review") implicitly admits this
gap.

### F3 — MCP-server v1 reopen-condition is unmeetable (HIGH)

Section 4 picks read-only MCP surface (`list_runs`, `get_run`,
`get_budget`) for v1, with write-verb unlock gated behind "≥2
operator IDEs for ≥30 days without a security incident."

Problem: read-only over MCP gives operators almost no value vs `gh
run list` or a regatta CLI. The interesting verbs (`dispatch`,
`approve`) are exactly the gated ones. So v1 ships with no realistic
consumer → no usage → reopen-condition never fires → write surface
never lands.

Counter-pick (what Devin/Cursor would do): they ship MCP **consume**
(regatta-as-client) only, never **expose** (regatta-as-server),
because exposing themselves to IDEs invites a competing front-end
that owns the operator relationship. Anthropic doing it for Claude
Code is the inversion — but regatta is not Anthropic.

**Fix:** either (a) scope v1 to a write-light verb that has a real
consumer — e.g. `mcp.regatta.approve(token)` so a phone-side MCP
client can clear an approval (matches #399 §2 G2 "mobile review");
or (b) drop MCP-server from top-3 and ship MCP-consume only. The
in-between read-only-with-no-consumer is the worst of both.

### F4 — Honeycomb primary contradicts self-host stance more than admitted (MEDIUM)

Section 3's adversarial-review note resolves the vendor-lock concern
by adding "Grafana/Tempo as fallback for self-host operators."
Customer-0 (#399 persona A) is the self-host operator. So Grafana is
the **primary** for the actual customer-0 — Honeycomb is the
secondary, called when persona B/C lands. The brief's framing is
inverted relative to #399.

**Fix:** restate the §3 primary as "self-host: `stdout` or local
Grafana/Tempo OSS; SaaS-when-it-ships: Honeycomb; LLM-specific:
Langfuse." Aligns with #399 MVR-1 / MVR-2 sequencing.

### F5 — E2B "SaaS canonical" premature; no SaaS exists (MEDIUM)

### F6 — Anthropic Skill format vs Claude Code plugins under-considered (MEDIUM)

Section 2 picks Anthropic Skill format (SKILL.md + YAML frontmatter)
and rejects building a regatta-branded marketplace. The brief does
not score **Claude Code plugin manifests** (the JSON-manifest +
permissions-scoped format Claude Code ships) as a separate candidate.
Plugins ship signed installation contracts; Skills ship as unsigned
markdown.

Regatta's load-bearing property is the **audit trail**. Skill-format
fits the authoring shape; plugin-manifest fits the installation+audit
shape. The brief should pick **both** — Skill format for the
markdown surface, plugin-manifest semantics for the install contract
in `regatta skill install`.

**Fix:** add Claude Code plugin manifest as a 7th row in §2's table;
expand the decision row to "Skill format for authoring, plugin
manifest semantics for install + signed audit."

### F7 — Reopen conditions inconsistent across sections (MEDIUM)

PR #399 §5 Gate 2 sets explicit measurable customer-count tiers (1 /
2 / 5 / 10 inbound asks). This brief's reopen conditions are loose:
"a paying customer files a request" (§1), "≥3 operators ask" (§2),
"a paying customer mandates it" (§3), "≥2 operator IDEs for ≥30 days"
(§4), "an operator surfaces a workflow" (§5), "cold-start latency
becomes the dispatch-loop bottleneck" (§6), "an operator needs
cross-team prompt sharing" (§7).

Three of seven are tool-checkable (§2, §4, §6); four are vague (§1,
§3, §5, §7). Drift from the precedent set by #399.

**Fix:** rewrite the vague reopen conditions to dashboardable
predicates — e.g. §1 "Pkl reopen when `inbound_customer_asks{wedge=
ide_authoring} ≥ 1`"; §5 "reopen when L4 reviewer false-positive rate
on `pr_merge_rate` panel exceeds 5% for a 7-day window"; §7 "reopen
when prompt-revision count per dispatch ≥ 3 within a 30-day window
(diff fatigue signal)."

### F8 — `.regatta/prompts/*.yaml` tree contradicts unified-substrate collapse (LOW)

`.regatta/`." The Phase X meta-dossier `docs/wedges/unified-substrate.md`

existing CAS blob store is the storage; Promptfoo is the eval CLI.
Aligns with #399 §3 W11 "plain sqlite-CAS over substrate
`blob_digest` column."

## Counter-pick — what Devin/Cursor would pick

Devin (Cognition) / Cursor would pick the wave-2 top-3 differently:

reasoning is correct in *principle*; F3 is about v1 sizing not the
choice of direction.
